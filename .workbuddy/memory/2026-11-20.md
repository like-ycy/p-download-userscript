## 打通 Chrome 标签页/页面数据访问通道

结论：osascript（AppleScript）在本机不可用，改走 CDP 成功。

- `osascript` 发 Apple Events 一路报 `-10004 权限违例`：不仅 Chrome，连 Finder 都失败；
  但 `tell application "Google Chrome" to get version` 能返回（走 bundle 静态信息，不发事件）。
  判断是宿主进程缺 Automation 授权 / 被 TCC 拦截，与 Chrome 的「允许 Apple 事件中的 JavaScript」开关无关。
- 发现 Chrome 主进程已在 `127.0.0.1:9222` 监听 DevTools 端口（HTTP `/json/*` 返回 404，
  但 `ws://127.0.0.1:9222/devtools/browser` 握手 101 可用）。
- 用 `uv run --with websocket-client` 直连 CDP，验证通过：`Target.getTargets` 列标签、
  `Target.attachToTarget(flatten)` + `Runtime.evaluate` 读正文/选中/执行 JS、`Page.captureScreenshot` 截图。

产出：`tools/cdp.py`（子命令 `list` / `read` / `shot` / `eval`，默认端点 `ws://127.0.0.1:9222/devtools/browser`）。
注意：本机 `ps` 在沙盒内外都可能被系统拦截，改用 `pgrep` / `lsof`。

## 弹窗问题：改成单连接 bridge

用户反馈每条命令都会让 Chrome 弹「允许调试」，每次都要手点。

根因：Chrome 144+ 从 `chrome://inspect/#remote-debugging` 开启的调试端口，**每个新的 WebSocket
客户端都会弹一次授权，且 Chrome 官方明确不做持久化记忆**（Web 上 cdp-share / chrome-cdp skill
等方案都是同一结论）。原实现每条命令 `create_connection` 一次，所以每条命令弹一次。

改造：`tools/cdp.py` 重写为 bridge 架构——`serve` 子命令独占唯一那条 Chrome WebSocket，
在 `/tmp/cdp-bridge-<uid>.sock`（权限 0600）上提供单行 JSON 协议，其余 CLI 命令一律转发，
不再直连 Chrome。target→session 缓存在 daemon 内，避免 session 堆积。握手超时放宽到 180s
（对话框打开期间 Chrome 挂起不回应），连上后命令超时回到 30s。

实测：一条 `serve` 之后连跑 status / list / read / eval / shot 五条命令，无新增弹窗。
